# jq.test compatibility baseline (historical)

Measured at 2026-09-04T23:40:36Z against jq 1.8.2 commit
`34f7186b86743a083a589741b6cea95293524108`.

> **Historical snapshot, not current release status.** The measurements,
> failure clusters, proposed work, and owner paths below describe the port at
> the stated timestamp. Those gaps were subsequently closed. The active parser
> is generated by GPPG from the maintained C#-action
> `src/DotNetJq/Grammar/parser.y`; the GPLEX lexer is maintained in
> `src/DotNetJq/Grammar/lexer.l`. jq's original C-action grammars are not
> committed, and production has no handwritten/template parser fallback. The
> parser guard requires 167 jq alternatives, 169 generated rules, 312 states,
> zero conflicts, and byte-identical `%left`/`%right` tables for every marked
> `%precedence` stand-in. The generated-parser Release promotion candidate
> passed 1,441/1,441 managed tests and proved the exact nesting boundary: 9,994
> levels succeed and 9,995 report bounded `jq: error: memory exhausted`.

## Measurement

The compatibility runner and library were rebuilt before measurement:

```text
dotnet build tools/DotNetJq.CompatibilityRunner/DotNetJq.CompatibilityRunner.csproj -t:Rebuild
Build succeeded. 0 Warning(s), 0 Error(s)
```

`tests/jq.test` was then executed in 22 separate 25-case processes, using
`--skip 0,25,...,525 --take 25` and a 25-second timeout per process. Every
slice completed normally. The aggregate result is:

| Fixture cases | Passed | Failed | Pass rate |
| ---: | ---: | ---: | ---: |
| 550 | 372 | 178 | 67.64% |

Failure phases:

| Phase | Count |
| --- | ---: |
| Compile message | 13 |
| Compile outcome | 14 |
| Runtime outcome | 97 |
| Output mismatch | 54 |

The deep-containment boundary regression at case 542 (depth 10,000) now
passes. Case 543 (depth 10,001) still fails because the managed implementation
returns `true` instead of raising `Containment check too deep`.

Potential gains sum to 178. The highest-leverage order is builtin binding, path
updates, error-value fidelity, then module support. Parser/module diagnostics
and deep-limit cases should be closed after their semantic outcomes are correct,
so exact-message work is not repeated around changing behavior.

## Reproduction

The runner's default fixture is the pinned checkout, so a representative slice
can be repeated with:

```text
dotnet run --project tools/DotNetJq.CompatibilityRunner --no-build -- \
  --fixture upstream/jq/tests/jq.test --skip 500 --take 25
```

No exclusion or expected-failure list was used. The official jq executable was
not invoked by the compatibility runner.
